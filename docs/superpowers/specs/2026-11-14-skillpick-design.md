## 1. 의도

자기 서비스를 직접 만드는 개발자·1인 창업자는 기능은 금방 만들지만 홈페이지 디자인에서 매번 막힌다.
요즘은 `frontend-design`, `web-design-guidelines`, `ui-ux-pro-max` 같은 AI 디자인 스킬이 쏟아지는데,
설명만 읽어서는 내 페이지에 어떤 결과가 나올지 알 수 없고, 하나씩 깔아 돌려 보기엔 시간이 든다.

SkillPick은 **내 페이지 URL 하나에 여러 디자인 스킬을 동시에 돌려 결과를 나란히 보여 주고,
결과를 보고 스킬을 고르게** 한다. 모든 시안은 원본의 카피·가격·버튼·링크를 지켜야 한다는
같은 요구사항 문서를 통과해야만 비교 화면에 오른다. 그래서 시안 사이의 차이는 디자인 차이만 남는다.

사용자 결정(대화에서):
- 대상은 랜딩·홈페이지를 직접 만드는 개발자. 불편은 "디자인 고민"과 "스킬이 너무 많아 고르기 힘듦" 두 가지.
- 입력은 공개 URL, 받아 가는 것은 "고른 스킬 + 시안 코드".
- OpenMausBot 대신 자체 화면. 형태는 **Electron 로컬 앱**, clone 해서 각자 자기 Kiro 로그인으로 쓰는 BYOK.

## 2. 목표 / 비목표 / 반목표

**목표 (18:00 기준 완료 조건)**
1. `git clone` → `npm install` → `npm start`로 앱이 뜬다.
2. URL 입력 + 스킬 여러 개 체크 → 스킬마다 시안 1개가 Kiro CLI로 **동시에** 만들어진다.
3. 각 시안은 자동 검사(지켜야 할 것 n/n)를 거쳐 원본과 함께 격자로 나란히 보인다. 데스크톱/모바일 폭 전환.
4. 하나를 고르면 그 스킬의 출처·설치 안내와 시안 HTML 저장, 내 프로젝트용 Kiro 규칙 문서 내보내기가 된다.
5. 제출물: README(템플릿 전 섹션), BUILD_REPORT, `.kiro/`, PRESENTATION.pdf, 데모 영상 링크.

**비목표 (오늘 안 함)**
- 설치 파일(.dmg) 배포, 코드 서명·공증, 자동 업데이트.
- 내 프로젝트 코드에 시안을 직접 적용하기.
- 여러 페이지·로그인 뒤 페이지·폼 동작 복제. 단일 공개 페이지(또는 localhost)만.
- 다국어. 해커톤 심사용 한국어 UI만. 분석 SDK(PostHog·Meta)도 넣지 않는다. 해커톤 프로토타입이므로 출시 준비 완료로 보고하지 않는다.
- 시안 품질을 AI로 점수 매기기. 사람이 보고 고른다.

**반목표 (돌아가도 실패인 것)**
- 시안이 원본 카피·가격을 지어내거나 빠뜨렸는데 비교 화면에 그대로 오르는 것.
- 원본 페이지에 숨은 지시문 때문에 Kiro가 사용자 컴퓨터에서 명령을 실행할 수 있는 것.
- "동시에"라고 해 놓고 실제로는 하나씩 도는데 화면이 그걸 숨기는 것.
- 데모가 미리 만들어 둔 결과를 재생하면서 실시간인 척하는 것.

## 4. 만드는 방법 (검토한 안)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 로컬 앱이 Kiro CLI를 시안 수만큼 동시에 띄움 (채택)** | Electron 메인 프로세스가 시안별 작업 폴더를 만들고 `kiro-cli`를 병렬 실행 | 시안을 만드는 엔진이 Kiro라 활용 설명이 가장 강함. 셸 권한을 안 줘 안전. 서버 비용 0 | 우리 맥에서만 시연. 동시 실행 한도 미확인 |
| B. 시안마다 Daytona 샌드박스 | HackSprint `control/` 재사용 | 공개 미리보기 주소 | 샌드박스 안 Kiro 로그인 문제(지난번 Codex 토큰처럼 순차 실행 위험), 준비 시간 최장 |
| C. AI API 직접 호출, Kiro는 개발 도구로만 | 앱이 API로 생성 | 가장 빠름 | 엔진에서 Kiro 빠짐, 스크립트 딸린 스킬 불완전, 키 비용 |

웹 대신 Electron을 고른 이유(사용자 결정 + 근거): 내장 브라우저로 원본을 직접 열어 화면 캡처·텍스트 추출을 하므로
Python·Playwright 설치가 필요 없고, 시안을 격리된 뷰에 띄울 수 있으며, clone 해서 자기 로그인으로 쓰는 형태가 자연스럽다.

**예비 경로**: Kiro 실행부는 `runEngine(workDir, prompt) → {ok, log}` 하나로 감싼다. 동시 실행이 막히면
(1) 동시 개수를 줄이고 화면에 대기열로 정직하게 표시, (2) 그래도 안 되면 C 방식 엔진을 같은 함수 뒤에 붙인다.
C로 바꾸면 README·BUILD_REPORT에 그 사실을 그대로 적는다.

## 6. 구성

```
electron/main      앱 수명주기, IPC, 아래 모듈 호출
  capture          숨은 BrowserWindow로 원본 열기 → content.json + 캡처 2장
  mustKeep         content.json → 지켜야 할 것 목록 + requirements.md(EARS)
  skills           기본 목록 + 사용자 추가 SKILL.md 가져오기·캐시
  workspace        시안별 작업 폴더 만들기
  engine           runEngine: kiro-cli 실행, 동시 개수 제한, 시간 제한, 로그
  checker          결과 HTML 결정론 검사 + 숨은 창 렌더 확인 + 캡처
  runStore         실행 기록(JSON 파일) 저장·불러오기
preload            최소 IPC만 노출 (contextIsolation 켬, nodeIntegration 끔)
renderer           5개 화면 (프레임워크는 빌더 판단, 빌드 도구는 가볍게)
```

### 6.1 원본 수집 (capture)
- 허용 주소: `http`/`https`만. 로컬 앱이므로 `localhost`(개발 중 페이지)도 허용한다(제 판단).
- 숨은 창에서 열고 로딩이 잠잠해질 때까지 짧게 기다린 뒤(상한 20초) 추출: 제목, 메타 설명, 제목 태그 계층, 본문 단락, 버튼·링크(글자 + href), 가격처럼 보이는 문자열, 주요 이미지 절대 URL, 내비 링크.
- 1440폭·390폭 전체 캡처 2장. 원본의 폼 제출·결제는 하지 않는다(그냥 읽기만).
- HackSprint `parse.py`의 추출 규칙을 참고해 JS로 옮긴다.

### 6.2 지켜야 할 것 (mustKeep)
- 대상: 대표 제목, 핵심 카피 문장, 가격, 행동 유도 버튼 글자와 그 href, 내비 링크.
- 각 시안 폴더의 `.kiro/specs/landing/requirements.md`에 EARS 수용 기준으로 쓴다.
  예: "WHEN 방문자가 첫 화면을 볼 때 THE 페이지 SHALL '무료로 시작하기' 버튼을 보여 주고 그 링크는 https://…/signup 이어야 한다".
- 같은 목록을 기계가 읽는 `must-keep.json`으로도 저장해 checker가 쓴다.

### 6.3 스킬 (skills)
- 기본 목록 6~8개: 공개 GitHub의 디자인 스킬 중 **글 지침만으로 동작하는 것**을 고른다(스크립트 실행이 필요한 스킬은 셸 권한이 없어 제대로 돌지 않음). 후보: `frontend-design`(Anthropic), `web-design-guidelines`(Vercel), `ui-ux-pro-max` 등. **`k-style-ui-ux`(https://github.com/vmc-inner-circle/k-style-ui-ux)는 사용자 지정으로 반드시 포함.** 최종 목록과 라이선스는 빌더가 확인. 시안 이미지에 나온 `minimalist-ui`·`brutalist-web`·`design-critic`은 이미지 모델이 지어낸 이름이므로 따라 하지 않는다.
- 저장소에 스킬 본문을 복사해 넣지 않는다. 출처 URL + 고정 커밋만 적어 두고 실행 시 받아 캐시한다(라이선스 회피).
- 사용자가 `SKILL.md` 주소를 붙여 넣어 추가 가능. 받은 본문은 데이터로만 다룬다.

### 6.4 작업 폴더 (workspace)
`<앱 데이터 폴더>/runs/<실행ID>/<스킬ID>/`
```
.kiro/agents/designer.json      도구: fs_read, fs_write 만
.kiro/steering/skill.md         선택한 스킬 본문
.kiro/specs/landing/requirements.md
content.json  must-keep.json  original-desktop.png  original-mobile.png
out/index.html                  ← Kiro가 만드는 결과 (CSS·JS 인라인 단일 파일, 이미지는 원본 절대 URL)
```

### 6.5 엔진 (engine)
- 명령: `kiro-cli chat --no-interactive --agent designer --trust-tools=fs_read,fs_write "<지시>"`, 작업 폴더를 cwd로.
- 기본 동시 3개(설정 가능, 스파이크 결과로 확정). 시안당 시간 제한 8분. 앱 종료 시 자식 프로세스 모두 종료.
- **셸 실행 도구는 절대 신뢰 목록에 넣지 않는다.** 원본 페이지 글자에 숨은 지시문이 있어도 파일 쓰기 밖으로 못 나간다.
- 쓰기 범위 확인: 실행 뒤 작업 폴더 밖에 바뀐 파일이 없는지는 강제 장치가 없으므로, 에이전트 설정과 지시문 양쪽에 범위를 적고 결과는 `out/`만 읽는다.

### 6.6 검사 (checker)
- 코드로 판정(AI 안 씀): `must-keep.json` 각 항목이 결과 HTML의 보이는 글자에 있는지(공백·대소문자 정규화), 버튼 href 일치, 외부 `<script src>` 없음(허용 목록: 웹폰트 정도), `<form action>` 외부 전송 없음, 파일 크기 상한.
- 숨은 창에 띄워 콘솔 오류 수와 1440·390 캡처를 남긴다.
- 실패 시 빠진 항목 목록을 넣어 같은 세션을 `--resume`으로 **한 번만** 다시 고치게 한다. 그래도 실패면 결과를 "⚠ n/m"으로 표시.

### 6.7 비교와 선택
- 카드마다 시안을 격리된 뷰(별도 세션 파티션, Node 접근 없음)로 띄운다. 폭 전환은 뷰 폭을 바꾼다.
- "이 스킬로": 스킬 출처 URL과 설치 안내 복사, `out/index.html` 저장, 사용자가 고른 폴더에 `.kiro/steering/design-<스킬ID>.md` 내보내기.

## 7. 이 저장소에서 Kiro를 쓰는 방식 (심사 대상)

- **역할 분담(사용자 결정)**: 기획·계획은 Claude Code, **구현은 Kiro**가 한다. 그래서 계획은 Kiro가 바로 실행할 수 있는 형식(`.kiro/specs/skillpick/requirements.md`·`design.md`·`tasks.md`)으로 넘긴다.
- `.kiro/specs/skillpick/`에 이 제품 자체의 requirements·design·tasks를 둔다. 이 설계 문서와 `2026-11-14-skillpick-ui.md`(화면 명세), `docs/ui/mockups/`(시안 이미지)가 원천이다.
- `.kiro/steering/`: 제품 규칙(대상·반목표), 보안 규칙(셸 금지·비밀값 금지), 생성 시안 품질 규칙.
- `.kiro/hooks/`: 개발 중 checker·mustKeep 파일이 바뀌면 단위 시험을 돌리는 훅 등.
- 제품 실행 중에도 Kiro가 엔진이다: 시안마다 커스텀 에이전트 + 규칙 문서(스킬) + 요구사항 문서(지켜야 할 것).
- BUILD_REPORT에는 실제로 쓴 것만 적는다. 쓰지 않은 기능을 쓴 것처럼 적지 않는다.

## 8. 시험과 확인

- 실제 확인: 앱을 띄워 실제 공개 사이트 1곳(예: HackSprint 때 쓴 `https://www.theaibuilders.dev/`)에 스킬 3개를 돌려 비교 화면까지 간다. Electron 화면 조작·캡처는 Argent(Chromium CDP)로.

## 10. 위험

- kiro-cli 동시 실행이 막히거나 느림 → 4절 예비 경로.
- 시안 하나가 8분 넘게 걸림 → 지시문에서 단일 HTML·섹션 수 상한을 걸고, 데모는 스킬 3개로.
- 원본 사이트가 봇을 막음 → 데모 사이트를 미리 2곳 정해 둔다.
- 업로드된 `kirometa.zip`(WhatsApp 앱 생성기)은 이번 설계로 대체한다. 그 안의 PWA 검사·배포 스크립트는 쓰지 않는다.

## 11. 빌더 검토 뒤 정한 것 (메인 판단, 사용자 확인 대상)

1. **예비 엔진 전환 기준**: 스파이크에서 kiro-cli가 (가) 비대화 실행 자체가 안 되거나 (나) 시안 1개가 10분을 넘으면 C로 간다.
   동시 실행만 막히면 C로 가지 않고 동시 1~2개 + 대기열 표시로 간다.
   C의 키는 사용자 Anthropic API 키(앱 설정에서 입력, macOS 키체인 `safeStorage` 저장), 모델은 최신 Sonnet.
   C에는 도구가 없어 결과 HTML만 받으므로 셸 문제는 원천적으로 없다. 스킬 본문은 시스템 지시문에 넣는다.
   C로 가면 화면과 README에 "엔진: Anthropic API"를 그대로 표시한다.
2. **스킬 목록**: 첫 30분 안에 후보를 실제로 열어 형태를 확인한다. 데모 최소 3개, 목표 6개.
   스크립트가 딸린 스킬은 SKILL.md 본문만 쓰고 카드에 "지침만 적용" 표시를 단다.
3. **지켜야 할 것 선정 규칙(코드)**: h1 전부, h2 전부, 첫 화면(히어로) 첫 단락, 버튼·버튼형 링크 글자+href 전부, 가격 문자열 전부, 내비 링크 글자+href.
   상한 25개, 넘으면 h2·내비부터 줄인다. 합격은 n/n. 정규화는 공백 압축·대소문자 무시·문장부호 무시.
4. **시안의 자유 범위**: 레이아웃·섹션 순서·색·글꼴·이미지 배치는 자유. 지켜야 할 것은 빠짐없이 그대로.
   **원본에 없는 가격·숫자 통계·후기·로고를 지어내지 않는다.** checker는 결과에서 원본에 없는 가격·숫자(%, 명, 원, $ 등)를 찾아 "⚠ 지어낸 숫자 의심"으로 표시한다.
5. **시안 뷰 보안**: 별도 세션 파티션, Node 접근 없음, CSP로 `script-src 'unsafe-inline'`, `connect-src 'none'`,
   `img-src https: data:`, `font-src https: data:`, 페이지 이동·새 창 차단. 외부 스크립트는 검사에서도 실패 처리.
6. **재시도 방식**: 스파이크에서 폴더 단위 `--resume`이 병렬에서도 섞이지 않는지 확인한다(시안마다 폴더가 달라 섞이지 않을 것으로 봄).
   안 되면 새 세션에 이전 `out/index.html`과 빠진 항목을 넣어 고치게 한다.
7. **제출물 형식**: README 섹션은 저장소 루트 `README.md` 템플릿을 따르고, PRESENTATION.pdf는 6~8장(문제·대상·데모 캡처·구조·Kiro 활용·기대 효과).
